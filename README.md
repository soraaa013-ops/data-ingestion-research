# data-ingestion-research

这项调研从一个很具体的问题出发：

> 我们已有一个 ML 平台，可以让用户查询业务数据库，把结果上传到 OBS/S3 作为训练数据。架构师认为这样会影响生产系统，也缺少数据授权。那么，这套设计应该怎么改？业界厂商究竟怎么做？

这份 README 是调研的阅读主线。我们用同一个例子，逐步改变需求，解释为什么会出现批量查询、只读副本、快照、增量查询和 CDC 等不同设计。每一步都说明：**遇到了什么问题 → 找到什么厂商证据 → 证据能说明什么 → 对我们的平台有什么影响**。

下面的客服场景、记录和时间都是为了讲解构造的例子，不是真实业务数据，也不是厂商客户案例。厂商功能附官方链接；对本平台的建议会单独说明。

## 1. 先把我们真正要做的事情讲清楚

假设客服部门想微调一个回答产品问题的模型。业务系统的 MySQL 中保存了已经处理完的工单：

| ticket_id | team | question | approved_answer | customer_phone | updated_at |
|---|---|---|---|---|---|
| 101 | 售后 | 如何申请退款？ | 请在订单页面提交申请 | 示例敏感字段 | 11-01 10:00 |
| 102 | 售后 | 商品损坏怎么办？ | 请上传照片并联系客服 | 示例敏感字段 | 11-02 09:00 |
| 103 | 财务 | 如何修改发票？ | 请进入发票管理页面 | 示例敏感字段 | 11-02 11:00 |

售后团队只需要自己的问答，不需要客户手机号，也不需要财务团队的数据。先假设每周训练一次，允许使用昨天的数据；稍后再讨论需求变化。

你现在的实现大致是：

```text
空间管理员配置数据库账号
    → 用户写查询
    → Kubernetes Job 连接数据库并执行
    → 结果写入文件
    → 上传 OBS，成为 dataset
```

用户可能提交这样的查询：

```sql
SELECT ticket_id, question, approved_answer, updated_at
FROM tickets
WHERE team = '售后'
  AND status = 'closed';
```

这里暂时不讨论微调算法。我们要解决的是：这批问答怎样从业务系统变成可靠的训练输入，同时不让导入操作拖慢业务。

注意，“只取自己的领域”不等于数据量必然小。即使最终返回几千条，数据库也可能为了找出它们扫描很多数据。因此要研究的是整个获取过程，而不只是导出的文件大小。

## 2. 第一个问题：用 SQL 从数据库导出，本身就是错误设计吗？

先查与你现有方案最接近的厂商实现，而不是先假设要改成数据湖。

阿里云 DataWorks 的 MySQL Reader 提供字段、过滤条件以及自定义 querySql。微软 Azure Data Factory 的 SQL Server 连接器也支持查询和分区复制。这说明“连接数据库，查询结果，再搬到目标位置”是正式的产品设计。[DataWorks 官方文档](https://www.alibabacloud.com/help/en/dataworks/user-guide/mysql-data-source)、[ADF 官方文档](https://learn.microsoft.com/en-us/azure/data-factory/connector-sql-server)

回到工单例子，用户选出售后问答，执行器负责搬运，这个方向有业界对应物。我们不能仅因为它使用 SQL 就判定要推翻。

但这里还没有回答“能不能查生产主库”。连接器文档只证明产品支持查询，不知道你的主库此时是否已经满负荷，也不知道用户写的查询是否有合适索引。

所以第一个阶段的结论是：

> 保留查询式导入作为候选。接下来要研究查询在哪里执行、做多少工作、谁来限制它。

对应细节：[阿里云怎样组织查询参数](docs/vendors/alibaba.md)、[微软怎样组织复制任务](docs/vendors/microsoft.md)。

## 3. 第二个问题：如果查询拖慢业务，应该改变哪一部分？

继续这个例子。只有一个团队偶尔导入时，系统可能很平稳。后来十个团队同时提交任务，每个任务又启动多个查询，业务数据库承受的是这些查询的总和。

Kubernetes 可以限制 Job 自身的 CPU，但 SQL 的扫描、排序和关联是在数据库服务器上完成的。仅给 Pod 限资源，并不能限制数据库做的工作。

这里有两类不同的改法。

### 3.1 仍然查询，但限制同时做多少工作

华为云 CDM 把迁移作业拆成任务，任务进入运行池，超过集群最大抽取并发数的任务排队。这是把“用户提交任务”和“任务立即全部运行”分开的设计。[CDM 官方说明](https://support.huaweicloud.com/intl/zh-cn/usermanual-cdm/cdm_01_0153.html)

我们可以借鉴排队，但还需要补上一层：按同一个源数据库统计所有团队的任务。假设测试表明某来源只能容纳两个并行抽取，就让其余任务等待。这里的“两个”只是示例，不是安全阈值。

还要能在运行太久或业务指标恶化时取消数据库查询。只把 Kubernetes Job 杀掉，不能未经验证就认定服务端查询已经结束。

这解释了为什么“只允许 SELECT”不够：它限制了某些操作类型，却没有回答这个 SELECT 会读多少数据、运行多久。

### 3.2 改变读取位置，让重查询避开正在服务业务的数据库

如果导出范围很大，单纯限并发仍然不合适，就研究专用读取副本或快照。

两者含义不同：

- 读取副本是另一份持续复制的数据，可以查询，但存在复制延迟和运行成本。
- 快照是一个时间点的数据副本，适合读取固定截面，不追求最新数据。

AWS RDS 提供从已有数据库快照导出到 S3 的机制。官方明确说明，**该导出过程**在后台运行，不影响活动数据库性能。注意，这句话描述的是从快照导出，不应扩大成“创建快照也永远没有影响”，更不能推广到所有数据库产品。[RDS 官方说明](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ExportSnapshot.html)

在示例中，如果售后团队接受昨天的数据，可以研究从昨天的快照产生训练输入；如果只需几条近期工单，为此导出一个很大的快照反而可能不划算。

这一阶段得到的判断是：**抽取范围小且可控，研究受控查询；范围大、重复扫描重，研究把读取移到副本或快照。**是否选用，仍需测量源负载和成本。

对应细节：[华为的并发调度](docs/vendors/huawei.md)、[AWS 的快照路径](docs/vendors/aws.md)、[几种读取方式的比较](docs/patterns/delivery.md)。

## 4. 第三个问题：每周都重新导出全部工单，是否浪费？

现在改变需求：工单越来越多，但每天只有一小部分新增或修改。每次重读全部历史数据，会做很多重复工作。

微软 ADF 给出的一种方法是记录水位。这里的“水位”就是上一次成功复制到哪里，例如上次处理到的更新时间。[ADF 增量教程](https://learn.microsoft.com/en-us/azure/data-factory/tutorial-incremental-copy-overview)

用我们的例子说明：

```text
上次成功处理到：11 月 2 日 00:00
这次选择的上界：11 月 3 日 00:00

读取这个时间区间中发生更新的工单
    → 写入并校验结果
    → 成功后把处理位置推进到新上界
```

这就叫增量查询。平台需要记住处理位置，并在重试时防止重复样本。它仍然查询数据库，只是不再每次读取全部历史。

但是，下面两个变化会暴露问题：

**变化一：旧工单被修改。** 如果只记“上次最大的 ticket_id”，101 号工单今天改了答案，它的 ID 没变，就会漏掉。用 updated_at 也需要保证每次修改都会更新该字段，并处理迟提交和相同时间戳。

**变化二：旧工单被物理删除。** 数据库里已经找不到这行，按更新时间查询也就读不到“这行被删除了”的信息。微软 Fabric 的文档明确区分了水位方式与能捕获删除的 CDC。[Fabric 增量说明](https://learn.microsoft.com/en-us/fabric/data-factory/incremental-copy-job)

所以，“加个定时任务，只查更新时间”只适合满足特定前提的数据。对会修改、删除的工单，我们需要更完整的变化信息。

对应细节：[微软：从全量到增量](docs/vendors/microsoft.md)、[漏数、重试和删除问题](docs/patterns/correctness.md)。

## 5. 第四个问题：需要知道每次增删改时，厂商怎么做？

这时再引入 CDC（Change Data Capture，变更数据捕获）。简单说，它利用数据库提供的变更日志或变更接口，读取“哪条记录新增、修改、删除了”，而不是反复查询整张业务表。

我们的工单可能产生：

```text
新增 101：退款问题，答案 A
修改 101：答案由 A 改为 B
删除 102：这条工单不应继续保留
```

Databricks 的 CDC 连接器把系统拆成持续采集的 gateway、临时保存采集结果的 staging，以及把结果应用到目标表的 pipeline。持续采集与下游处理可以有不同节奏。[Databricks CDC 架构](https://docs.databricks.com/aws/en/ingestion/lakeflow-connect/cdc-overview)

这解决了一个容易忽略的问题：**每周训练一次，不代表每周读取一次日志就一定来得及。**如果日志在两次训练之间已经过期，下周就无法从旧位置继续。持续采集把变化先保存下来，训练时再构建数据集。

代价是采集服务需要持续运行，还要管理初次全量、日志保留、断点恢复和存储。CDC 并不是一个完全没有源端成本的“安全连接开关”。

同一家 Databricks 也提供定时查询方式，不需要这套常驻采集网关。这是一个很有价值的对照：厂商本身也没有要求每个场景都采用 CDC。[Databricks 查询式连接器](https://docs.databricks.com/aws/en/ingestion/lakeflow-connect/query-based-overview)

对我们的平台，判断变成了：

> 如果每周只需要一份最新问答，受控批量或增量查询可能已经够用。如果要持续跟踪修订和删除，且简单查询无法可靠覆盖，再评估 CDC。

对应细节：[Databricks 两种运行方式](docs/vendors/databricks.md)。

## 6. 第五个问题：CDC 已经写入对象存储，为什么还不能直接训练？

Google Datastream 可以把变更交付给对象存储。其事件文档说明，事件可能重复到达，也不保证按发生顺序到达，消费者需要利用元数据处理。[Google 事件说明](https://docs.cloud.google.com/datastream/docs/events-and-streams)

假设我们收到下面的文件内容。这里是教学示例，不是 Datastream 的真实字段格式：

```text
事件 e2：把 101 的答案改为 B
事件 e1：新增 101，答案为 A
事件 e2：把 101 的答案改为 B（重试导致重复）
```

如果把三行直接变成训练样本，会同时得到旧答案和重复答案。如果简单按文件到达顺序覆盖，第二行还可能把新答案 B 覆盖回 A。

因此要先根据来源的事件顺序与标识，还原“101 当前的正确答案是 B”。这一步叫状态重建，也就是把变化记录应用到一份当前数据上。

得到正确的工单状态后，还要做 ML 准备：选出获准的问答、检查空答案、去重、分开训练和评测数据，最后生成训练格式。例如：

```json
{"messages":[{"role":"user","content":"如何申请退款？"},{"role":"assistant","content":"请在订单页面提交申请"}]}
```

这个转换由 ML 平台完成是合理的；数据库搬运产品不自动知道什么是合格训练样本。

最后，需要发布一个固定版本，例如售后问答 v3。训练引用 v3，而不是读取一个还在不断上传的目录。记录这个版本包含哪些文件和它们的校验和的清单，叫 manifest；它是为了防止半份数据被训练读到，并让训练可以复现。

对应细节：[Google 的事件交付](docs/vendors/google.md)、[文件到可训练版本之间的步骤](docs/patterns/correctness.md)。

## 7. 第六个问题：数据库账号能读，是否就代表用户可以拿去训练？

回到最开始的表。平台使用的共享账号可能读得到所有团队和 customer_phone，但售后团队这次只需要自己的 question 和 approved_answer。

“账号能读”说明执行器具备技术访问能力，并没有表达：

- 这次允许复制售后还是所有部门的数据；
- 手机号是否允许离开业务系统；
- 这些内容能否用于训练，以及谁能使用导入后的数据集。

这就是为什么要把**连接配置**与**数据使用授权**分开。

本项目建议把一次授权写成业务上能读懂的内容，例如：“售后空间可为问答微调读取已关闭的售后工单，仅包含指定字段，有效期到某日，输出只能进入指定 dataset。”这是我们的平台设计建议，不是声称某家产品已经替我们完成审批。

用户仍然可以写 DSL，但执行的最终查询必须落在获准范围内。比如用户去掉 team 条件，不能因为语句仍然是 SELECT 就允许执行。原始问答中也可能含手机号，因此只去掉 customer_phone 列未必足够，正文处理也应纳入数据准备。

同时，授权不应到“导入成功”就结束。如果 102 号工单后来被要求移除，要知道哪些 dataset 包含它，以及哪些训练使用过这些版本。源库删除不会自动清理 OBS 中的旧文件。

对应细节：[用具体对象表达授权和生命周期](docs/patterns/governance.md)。各厂商治理产品如何实现这些能力仍需深化，当前不能把设计建议当作已完成的合规证明。

## 8. 把上面的问题合起来，我们究竟建议怎样改？

我们不是因为看到某个产品有 CDC 就全盘改成 CDC，也不是因为担心主库就先建一个企业数据湖。上面的每一条设计都对应一个已经解释过的问题：

| 遇到的问题 | 需要增加或选择的设计 | 放在现有平台哪里 |
|---|---|---|
| 多团队导入叠加，影响源数据库 | 源级排队、超时、取消；必要时副本/快照 | Job 调度与来源配置 |
| 重复读取全部历史 | 有前提的增量查询 | 导入任务的状态管理 |
| 需要持续跟踪修改和删除 | 按需选择 CDC | 独立的持续采集服务 |
| 事件重复、乱序或批次失败 | 去重、状态重建、可恢复的处理位置 | 导入后处理 |
| 原始业务记录还不是训练样本 | 清洗、格式转换、训练评测划分 | ML 数据准备 |
| 训练读到半份数据，难以复现 | 校验后发布固定 dataset 版本 | 现有 dataset 服务 |
| 共享账号权限大于用户用途 | 数据范围和用途授权，执行时校验 | 控制面与发布前检查 |

因此，一个适合先验证的方案仍然可以很轻：

```text
用户选择来源和获准数据范围，编写查询
    → 平台检查查询范围，并按来源预算排队
    → Kubernetes Job 从选定来源抽取数据
    → OBS 暂存本次结果
    → 清洗并构建问答样本
    → 校验后发布 dataset v3
    → 训练任务固定使用 v3
```

如果后续需要 CDC，只替换或扩展前面的获取方式，后面的样本构建和 dataset 发布继续复用。暂存区可以是现有 OBS 的独立目录，无需先建设统一数据湖。

对于架构师的两点质疑，现在可以给出更准确的回答：

**生产稳定性：**只检查 SELECT 确实不够。但“所有数据库查询都不允许”也不是从这些厂商资料能得出的结论。应该先讨论具体工作量和隔离方式，再用测试确认。

**数据授权：**空间管理员能配账号，不等于已定义谁可以把哪些内容用于训练。这个缺口需要补齐，并贯穿到复制后的文件和训练版本。

完整落地分析见[当前方案逐项匹配](docs/scenario/fit.md)和[参考架构](docs/scenario/architecture.md)。

## 9. 这个调研项目接下来怎么推进？

前面是已经形成的阅读主线，不代表所有细节已经研究完。我们按“要解决的问题”继续推进，再用厂商实现检验答案：

| 顺序 | 继续问什么 | 去哪里读或补证据 | 产出 |
|---|---|---|---|
| 1 | 每家产品实际怎样执行、控制负载、恢复？ | [六家厂商专题](docs/vendors/index.md) | 可核验的机制和限制 |
| 2 | 换成 Mongo、ES、Hive/DWS 后，哪些假设失效？ | [来源适配分析](docs/sources/source-adapters.md) | 每种来源的查询、分页、增量与删除差异 |
| 3 | 哪些条件下选查询、副本、快照或 CDC？ | [模式比较](docs/patterns/delivery.md) | 有前提的选择依据 |
| 4 | 哪些设计可以直接用在现有平台？ | [场景匹配](docs/scenario/fit.md) | 保留项、改造项与不需要引入的能力 |
| 5 | 怎样证明方案真的有效？ | [验证计划](docs/scenario/validation.md) | 慢查询、失败重试、删除、撤权等测试 |
| 6 | 哪些结论已经有证据，哪些仍待确认？ | [汇总报告](reports/summary.md) | 架构评审可用的阶段性结论 |

目前尚未做负载实测，也没有完成全部来源版本、厂商治理产品及成本的验证。尤其华为逐连接器能力仍需深入，不能因为同属 OBS 生态就直接认定最适合。
