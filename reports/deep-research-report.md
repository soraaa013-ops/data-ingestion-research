# 深度报告：企业怎样把 IT 系统数据交给 ML 平台

本报告对应 2026-11-10 的公开资料调研。研究对象包括云厂商、独立连接器、湖仓平台和企业工程案例。它回答架构选择问题，不声称覆盖所有产品，也不替代实际版本的兼容性测试。完整推导按顺序保存在 [12 篇教程](../docs/deep-dive/README.md)，原始信息入口和阅读记录保存在[本轮证据目录](../research/rounds/2026-11-10-deep-dive/README.md)。

## 1. 先回答：现有设计是否应该推翻？

不应仅因为“连接数据库执行查询”而推翻。查询式复制是正式产品能力，前轮已经在 DataWorks、ADF 中确认，本轮又检查了 CDM 逐来源参数，以及 Airbyte、Fivetran 等连接器的初次读取方式。数据总要通过某种方式离开源系统：查询、快照、日志、业务 API 或业务方生成的文件。没有一种方式天然没有源端成本。

但你目前描述的“账号 + 用户 DSL + Job + 文件上传”只呈现了执行路径，没有充分描述生产负载预算、全量与增量交接、恢复、授权和发布协议。应补全这些责任，再决定哪些由自己的平台承担、哪些交给连接器或现有数据平台。具体对照见[连接器内部](../docs/deep-dive/02-connectors.md)与[现有平台改造](../docs/deep-dive/10-your-platform.md)。

架构师的第一条意见可以改写成一个更可执行的要求：**不能让不受约束的用户抽取任务直接消耗生产数据库资源；读取位置和读取预算必须经过设计。**这不同于一概禁止连接生产系统。架构师的第二条意见则指出了真实缺口：能使用账号读取数据，不等于有权把数据复制后用于训练。

## 2. 把“搬数据”拆成一条能检查责任的链路

继续 README 中的售后工单例子。ML 用户要的是一份稳定的问答训练集，但业务数据库提供的是持续变化的业务记录。中间至少需要完成这些工作：

```text
业务库 / 业务接口 / 业务交付文件
    → 初次读取 + 后续变更获取
    → 可恢复的缓冲或暂存
    → 去重、合并、删除处理、授权字段转换
    → 不可变 dataset 版本 + manifest
    → 训练任务按版本读取
```

每个方框不一定对应一个新服务。每周一次的小批量任务，可以在一个受控 Job 中完成读取和转换；持续复制则可能由共享采集服务负责，训练集构建仍由 Job 完成。关键是不能因为图上省略了一层，就把这一层的责任也省略掉。[全景解释](../docs/deep-dive/01-map.md)

在这个分解下，数据湖也更容易理解：它可以承接中间状态并供多个消费者复用，但不能凭空解决“如何读取业务系统”的第一跳。反过来，没有统一数据湖也不意味着必须为每个用户重复扫描业务库。

## 3. 厂商究竟做了哪些不同设计？

下面比较责任分工，而不是按品牌排名。每一行都链接到具体例子和原始资料。

| 面对的问题 | 产品怎样处理 | 对本平台的含义 |
|---|---|---|
| 周期性取得表数据，失败后继续 | Airbyte 组织 source、destination 与状态；Fivetran 对 MySQL 初次读取及日志/其他增量机制给出具体行为 | 连接器的价值包括恢复，不只是执行 SQL；[细读](../docs/deep-dive/02-connectors.md) |
| 连续获取行级变化 | Debezium 协调快照、日志位置与后续事件 | 自建 CDC 要承担日志保留、模式历史与目标合并；[细读](../docs/deep-dive/02-connectors.md) |
| 不能使用日志，但能周期查询 | Confluent JDBC 按 ID/时间戳等轮询；Databricks 提供 query-based 路径 | 游标有适用条件，删除和关联表变化不能自动解决；[细读](../docs/deep-dive/03-lakehouse.md) |
| 想把数据库变化变成湖仓表 | Databricks managed database connectors、Snowflake Openflow、AWS zero-ETL 分别托管不同范围的复制与应用 | 托管程度与支持组合不同，不能把支持某源等同于支持 OBS dataset；[细读](../docs/deep-dive/03-lakehouse.md) |
| 外部生产者已经能产出变化文件 | Fabric Open Mirroring 定义 landing zone 和行操作协议，由平台生成可查询表 | 可以借鉴交付协议，但它不是源数据库采集器；[细读](../docs/deep-dive/03-lakehouse.md) |
| 文件已经在对象存储 | Databricks Auto Loader 跟踪并处理到达的文件 | 文件进入湖之后的可靠处理，与源端抽取是两项工作；[细读](../docs/deep-dive/03-lakehouse.md) |
| 国内云数据库到对象存储或消息系统 | CDM 按来源定义查询/分页；DRS、DataWorks、DTS 提供不同同步链路 | 应逐组合核对，不从同品牌另一产品推断能力；[细读](../docs/deep-dive/04-china-cloud.md) |
| 数据库在企业内网 | ADF self-hosted runtime 将执行放到可访问来源的位置 | 网络可达和负载隔离是两个问题；[细读](../docs/deep-dive/06-network-api-files.md) |

本轮一个重要修正是：CDC 是一种变更获取机制，不是固定的调度模式。Airbyte 可以按同步周期读取日志；Databricks 的受管数据库路径则有持续运行的采集网关。因此，“我们每周训练一次”既不能直接排除 CDC，也不能证明需要全天运行整套训练链路。[Airbyte 原文](https://docs.airbyte.com/platform/understanding-airbyte/cdc)

另一个修正是：联邦查询未必把工作移出生产系统。Databricks 区分查询联邦和目录联邦，前者可能在远端数据库执行查询。评估“复用现有数据平台”时，要查明读到的是已复制的数据，还是又把查询送回业务库。[Databricks 原文](https://docs.databricks.com/aws/en/query-federation)

## 4. 企业案例解释了升级架构的触发条件

Uber 的历史 DBEvents 文章讨论了全量读取与生产负担，以及持续事件链路如何支持数据分析；LinkedIn 的材料展示了大量独立搬运任务带来的维护问题与统一框架需求；Netflix 的 DBLog 论文进一步研究如何把分块读取与同时发生的日志变化协调起来。

这些案例共同提示我们：当消费者数量、更新要求和恢复要求增加，企业通常需要共享采集、统一状态管理和明确的交付协议。但它们不能证明一个部门级周批量任务也需要复制整套大型平台。[案例推导及年代边界](../docs/deep-dive/05-enterprise-cases.md)

例如，十个团队反复提取同一张工单表时，单纯给每个团队增加 Job 可能重复消耗来源资源。此时共享一次变更采集，再分别生成授权的领域 dataset，才是值得研究的升级方向。是否划算，取决于重复读取成本与长期运行成本的比较，而不是是否用了 Kafka 或湖仓。

## 5. 对你当前平台，保留三条路线

### 路线 A：受控的批量抽取与 dataset 发布

适合低频、有明确范围、可以接受批次延迟的导入。保留 Kubernetes Job 和 OBS/S3 dataset，但引入来源登记、数据范围授权、来源级并发预算、服务端超时和取消、确定的分页/快照策略，以及成功校验后再发布的流程。

读取位置可以是经评估的主库、专用副本或快照导出，不能仅凭“SELECT”判定安全。用户仍可以表达查询需求，但不应将原始 DSL 直接拼进 shell 或脚本源码；不同引擎要分别验证语法和可执行能力。一个复杂查询的代价也不是通用 SQL 白名单能够判断的。

这条路线最贴近现有架构，应该作为条件成立时的有效方案保留，而不是被当成临时错误。

### 路线 B：共享采集，按领域构建训练版本

适合多个消费者重复读取相同来源、变化频繁，或者需要处理更新和删除的场景。独立采集服务完成初次全量和后续变化接续，保留可恢复状态；领域构建 Job 读取已同步数据，完成筛选、脱敏和样本转换，发布 dataset。

这条路线不要求先做全企业数据入湖。共享范围可以限定为批准的表和领域。但持续服务必须有监控、日志保留预算、重建流程和维护者。源端负载也没有消失：例如 DTS 文档提示，选择少数表仍可能读取整个数据库的日志。[DTS 原文](https://www.alibabacloud.com/help/en/dts/user-guide/data-synchronization-scenarios)

### 路线 C：消费已有企业数据平台的受治理交付

如果企业已经维护了可靠复制、可解释的新鲜度和授权机制，ML 平台可以从受治理表或导出接口获取数据。接入前仍需确认源到平台的完整性、删除传播、权限适用范围，以及是否可以稳定导出为训练版本。

不必为了“完整架构”重新做一套已有采集；也不能因为数据来自湖仓就默认已经满足训练用途授权。直接对象存储读取和 SQL 查询权限可能走不同执行路径。

此外，三条路线都允许业务方通过批量 API 或版本化文件主动交付。它是来源责任的另一种安排，不是只能作为数据库接入失败后的补救。[架构与用户流程](../docs/deep-dive/10-your-platform.md)

## 6. 授权与可靠性要沿着复制过程继续生效

以工单 101 为例：业务账号能读取整张表，但训练可能只获准使用售后团队的问答字段。审批对象应包含来源、行列范围、用途、接收空间和有效期。执行器只获得完成任务所需的凭据，产出文件不能因为放进公共 bucket 路径而绕过原来的范围限制。

源端删除也需要先定义语义：它可能表示当前状态不再包含这条记录，或者要求清理历史副本。两者对 dataset 版本、缓存、已启动训练任务的影响不同。平台应记录可追溯关系和撤销状态，不能把删除源表记录等同于自动清除了所有下游副本。[权限推导](../docs/deep-dive/08-governance.md)

正确性方面，必须区分“已从源读取”“已可靠保存”和“已作为训练版本发布”。只有文件上传成功还不够：失败重试、重复事件、字段变化、删除及初次全量期间的更新都可能改变最终内容。[生命周期与发布协议](../docs/deep-dive/07-lifecycle.md)

## 7. 哪些结论可以采用，哪些需要继续核验？

可以采用的是责任分解和条件化选型：保留批量任务、将持续采集独立出去、用版本化交付连接 ML 消费；不把只读、CDC、agent、湖仓或零 ETL 当作安全和正确性的自动保证。

仍需核验的是具体候选的引擎版本、权限要求、网络可达、目标格式、区域可用性、许可证和计费，以及在给定负载下的表现。本轮没有执行压测，没有提供未经测量的“安全并发”或吞吐数字。所有测试场景和成本口径已保存在[验收与成本文档](../docs/deep-dive/12-cost-validation.md)。

下一步不是继续堆积品牌名单，而是依据目标场景选择路线，再逐项核验最接近的两三种实现。为了让这一过程可复查，本轮保留了[结论证据映射](../research/rounds/2026-11-10-deep-dive/claims.md)、[修正记录](../research/rounds/2026-11-10-deep-dive/corrections.md)及来源卡。新增证据可以修正结论，而不会覆盖掉中间研究过程。
