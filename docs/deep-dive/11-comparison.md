# 11｜横向比较：每种方案帮你搬到哪一步？

本表用于拆责任，不是排行榜。来源链接进入各专题，专题再连接官方原文。产品功能依版本/目标而变，空白不代表不支持。

| 产品/模式 | 取得源数据 | 交付或处理位置 | ML 平台仍需负责 | 最值得借鉴 |

| [ADF / CDM / DataWorks 批量](04-china-cloud.md) | 查询/分片等连接器 | 文件或指定目标 | 范围授权、样本、版本 | 统一任务配置与调度 |

## 为什么不直接标“适合/不适合”？

同一产品支持 MySQL，不代表支持当前版本、主从拓扑、所有数据类型、任意 SQL、所有 DDL 或 OBS 目标。“是否合适”至少需要六个事实：来源版本、访问路径、数据变化语义、目标格式、时效/容量、维护成本。

因此先用硬门槛排除，再比较偏好：

| 硬门槛 | 必须能回答的问题 |
|---|---|
| 正确拿到数据 | 初始化、修订、删除、结构变化是否覆盖？ |
| 可运行 | 实际私网、身份、来源/目标兼容吗？ |
| 可恢复 | 检查点丢失或日志过期怎么办？ |
| 可限制影响 | 并发、超时、取消、回填预算如何生效？ |
| 可限制使用 | 最终表达式与输出权限是否在授权内？ |
| 可消费 | 交付事件、当前表还是固定版本？ |

然后比较自建工时、持续运行成本、未来来源扩展和已有平台复用。无负载数据时不给精确总分。

## 对你的近期候选排序（研究建议）

最先验证现有受控批量 + OBS 发布，因为改造范围最小；如果容量不满足，加入已存在的副本/导出路径；如果变化完整性或重复消费需求驱动，再选择托管或自建 CDC；已有企业湖仓则先检查能否复用其可靠副本。

这不是对某厂商采购的推荐，而是按需求逐步增加能力的顺序。
