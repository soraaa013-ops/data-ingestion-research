# 08｜数据搬进湖或 ML 平台后，权限在哪里执行？

继续用售后工单例子。源库账号能读所有工单，售后用户只应使用本部门获准的问答。把数据放到湖仓，是否自动继承这一限制？必须逐层回答。

## 厂商实际提供的边界

AWS Lake Formation 的过滤规则作用于与它集成的引擎及所支持的表/查询能力。[官方限制](https://docs.aws.amazon.com/lake-formation/latest/dg/data-filtering-notes.html)，[N23](../../research/rounds/2026-11-10-deep-dive/sources/N23.md)。

Databricks Unity Catalog 把存储凭据与外部路径组合成可授权对象，让使用者通过授权访问，而不一定直接得到长期凭据。[External locations](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-external-locations)，[N24](../../research/rounds/2026-11-10-deep-dive/sources/N24.md)。

这两类事实支持“凭据与用户权限分开”的设计，但不证明任意外部 Kubernetes Job 下载原始文件时仍受相同的行列规则约束。

## 一条具体绕过路径

假设查询引擎只向售后用户展示 team='售后' 的行，但用户同时拿到了包含全部工单的桶读取权限。他绕开查询引擎下载底层文件，就可能看见更多内容。

这是对多路径访问的工程推演，不是针对某产品的漏洞指控。解决办法是让实际存储权限与受控查询路径匹配，或者只交付已经按范围生成的独立文件，而不是只在目录界面显示过滤标签。

## 建议把四份责任写清楚

| 责任 | 工单例子 | 谁来落实 |
|---|---|---|
| 技术连接 | 执行器能连接工单库 | 来源配置与密钥/网络管理 |
| 数据范围 | 只能取售后、指定字段 | 源权限、最终查询校验或数据交付合同 |
| 使用目的 | 允许用于某类训练 | 业务数据负责人及适用策略 |
| 复制后访问 | 只有获准训练任务能读输出 | dataset 权限与对象存储权限 |

空间管理员可以管理空间，不应仅因能输入密码就自动拥有批准所有源数据用途的权力。

## 不让审批成为每次运行的手工瓶颈

可把重复低风险范围预授权一段时间。用户在授权范围内调参数，平台自动检查并运行；新增敏感字段、更换用途或目标空间才触发重新评估。这是本平台建议，不是法定流程或厂商默认功能。

批准对象应绑定范围、用途、身份、目标、期限和策略版本。执行前及发布前都检查状态，防止长任务运行中授权已撤销但最终仍发布。

## 原始区与模型关联

正文里可能含手机号，只裁掉 customer_phone 列不够。原始区、临时文件、失败样本、运行日志也在数据处理范围内。对数据最小化的判断需要落在具体内容和用途上。

撤销应能找到相关 dataset 和训练任务。已经训练的模型不会因删除源文件自动消除影响；是否重训、停用或采取其他措施，需要另行判断。技术血缘让这种判断可执行，但不替代法律或业务决策。

这一章只研究技术及职责机制，不声称已经完成特定行业或司法辖区的合规认证。
