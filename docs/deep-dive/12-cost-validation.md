# 12｜怎样证明它搬得对、代价合理？

公开文档能帮助决定候选，不会替你证明当前生产库的 SLA。这里提供可执行的验证设计，明确没有运行这些实验。

## 把“生产稳定”转成可观察结果

构造有背景业务请求的隔离环境，先测无导入基线，再加入相同数据范围的不同策略。分别观察业务 p95/p99、数据库 CPU/IO、连接数、锁等待、复制延迟、任务耗时、取消后残留查询与恢复时间。

不能只测“导出用了几分钟”。最快的方案可能让业务最慢。首次全量、稳态增量、失败追赶应分开测，不能只拿 CDC 稳态与批量全量对比。

## 正确性用事先知道答案的数据验证

准备工单 101–110，包含 NULL、长文本、重复更新时间、附件、已删除和晚提交记录。保存预期状态，再执行：

1. 初次读到一半修改 101，检查最终是否新答案。
2. 同时间戳两条记录，中途失败，检查是否漏一条。
3. 删除、软删除、TRUNCATE 分开测试。
4. 上传完成但进度提交前崩溃，检查是否重复发布。
5. 增量期间加列/改类型，检查是否静默截断。
6. 撤销授权，检查已运行任务能否继续发布。
7. 超过日志保留窗口后重启，检查是否明确失败/回填。
8. 附件链接过期或文件缺失，检查 dataset 是否被错误标为完整。

这些为设计用例，不能把预期行为写成已通过结果。

## 日志保留的简单算例

假设每天产生 10 GB 日志，最坏中断两天，恢复后净追赶速度有限。至少要按中断积压及追赶期间新增量规划可用保留空间，而不只按“每天同步一次”判断。数字是教学构造，真实变化量与压缩不同。

一个必要但不充分的检查是：

```text
可用日志窗口 > 最大调度间隔 + 最大中断 + 追赶时间 + 余量
```

还要检查持续消费吞吐是否大于变化产生速率，以及源或复制槽保留过多日志会不会耗尽磁盘。保留无限日志不是免费安全措施。

## 总成本应该怎么算？

```text
周期总成本 =
  首次/重同步摊销
  + 源侧新增资源或副本
  + 采集与转换计算
  + 缓冲/目标存储及请求
  + 网络流量
  + 值守、升级和故障恢复工时
```

对于微调，再除以成功发布且真正使用的数据集数量。每周只用一批数据，却全天维持网关和状态合并，可能很贵；十个团队共享同一副本则可能划算。没有实际输入参数时不制造价格排名。

## 验收表与实现绑定

| 项目 | 验收结果应包含 |
|---|---|
| 源保护 | 基线与导入时指标、配置、触发暂停的阈值 |
| 数据完整 | 预期集合与实际集合差异，而非只看记录数 |
| 恢复 | 失败点、检查点、重试次数、最终重复/缺失 |
| 权限 | 实际执行范围、拒绝用例、存储访问验证 |
| 版本 | manifest、文件 hash、转换版本、源边界 |
| 成本 | 运行时、字节量、保留量、维护工时估计依据 |

阈值由实际业务目标确定。本项目提供研究与验收框架，不编造一个适用于所有数据库的并发或延迟阈值。
