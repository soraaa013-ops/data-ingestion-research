# 05｜企业为什么建设自己的 ingestion 平台？

产品文档说明“能做什么”，企业工程文章帮助理解“为什么要这样做”。这里选三类不同问题，不用大厂名称替代适用性分析。案例是历史公开记录，不代表它们在 2026 年的全部架构。

## Uber：重复全量读取开始同时伤害新鲜度和生产负载

Uber 在 2019 年的 DBEvents 文章中回顾：大规模并行读取业务库再写入 Hadoop，既重复搬运大量未变数据，也对业务请求造成压力。随后用来源捕获、Kafka 和增量写入湖的组件分工改善链路。[工程原文](https://www.uber.com/ch/en/blog/dbevents-ingestion-framework/)，[N28](../../research/rounds/2026-11-10-deep-dive/sources/N28.md)。

把它缩小成客服例子：每天十万张新工单并不等于要每天重读过去全部工单；变化越少、历史越大，重复全量浪费越明显。这是解释，不是 Uber 的原始数字。

值得借鉴的顺序是：先明确对数据新鲜度、质量和效率的要求，再引入共享变化链路。不能反过来因为 Uber 使用 Kafka/Hudi，就要求一个每月微调项目照搬同样基础设施。

它支持架构师“高并发全量扫描有风险”的担忧，但不是“所有查询都禁用”的证据。

## LinkedIn：问题来自许多各自维护的小脚本

LinkedIn 的 Gobblin 介绍回顾多条定制流程引发的质量、元数据和运维负担，进而建设可扩展的统一框架。[工程原文](https://engineering.linkedin.com/teams/data/analytics-platform-apps/analytics-platforms/gobblin)，[N29](../../research/rounds/2026-11-10-deep-dive/sources/N29.md)。

你的平台很容易遇到相似演进：MySQL 脚本自带重试，Mongo 脚本另存游标，ES 脚本失败后只从头开始。用户界面看上去统一，后台的恢复与审计却是五套规则。

可迁移的经验是统一任务合同、进度、质量指标和发布方式，同时允许不同来源有不同读取实现。不是强行把所有系统翻译成同一种 SQL。

LinkedIn 的另一份团队介绍还包括 API 和媒体文件集成。[原文](https://engineering.linkedin.com/teams/data/analytics-platform-apps/big-data-engineering/data-integration)，[N30](../../research/rounds/2026-11-10-deep-dive/sources/N30.md)。这提醒我们，微调数据很可能包含附件和有期限链接，数据库表搬完并不意味着业务内容已搬完。

## Netflix DBLog：回填时不能让旧值覆盖新值

原作者的 2020 论文研究了分块读取与日志捕获的交接。[论文](https://arxiv.org/abs/2010.12597)，方法补读见 [N33](../../research/rounds/2026-11-10-deep-dive/sources/N33.md)。

它在源端专用水位表产生低/高标记，把一块读取放进日志窗口；窗口内有变化的键不再使用冲突的读取结果。方法有主键范围扫描、非陈旧读取等前提。这里的水位不是 updated_at 查询水位，且需要源端写标记。

用自拟例子理解这个问题：回填读到 101 的旧答案 A，紧接着日志给出新答案 B。如果后面再把 A 写到目标，就发生倒退。协调两路输入的目的就是避免这种倒退，并允许暂停回填而保留恢复进度。

论文对其他工具的对比属于 2020 年，不能拿它否定今天 Debezium 已有的能力。本文没有复现论文性能，也不把“少锁”表述扩大为“零源端成本”。

## 三个案例放在一起说明什么？

| 案例 | 原始困难 | 对当前平台的启示 |
|---|---|---|
| Uber | 大规模重复全量与时效 | 有明确频率/规模需求时升级持续增量 |
| LinkedIn | 多条脚本各自维护 | 统一执行、状态、验证和可观测性 |
| Netflix | 回填与日志互相覆盖 | 不手工拼接快照/CDC，采用有协议的实现 |

这些证据说明企业会依据瓶颈演进，不存在从小规模第一天就必须部署全部组件的单一路线。
