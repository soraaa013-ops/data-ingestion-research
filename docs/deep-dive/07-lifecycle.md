# 07｜一次搬运从开始到可重跑：用故障把边界讲清楚

本章是跨厂商事实支持下的设计推演，不是某个产品的完整协议复刻。连接器机制见[02](02-connectors.md)，文件协议见[03](03-lakehouse.md)。

## 第一步：先声明要的是哪一种结果

假设导入 11 月的售后工单。有三种不同承诺：

- “本次逐批读到的结果”，可能不对应全库同一时刻。
- “截至某个一致性位置的状态”，需要源或连接器支持对应截面。
- “这个时间段内发生的事件”，可能包含同一工单多个版本。

不要把三者都叫“快照”。训练通常需要固定输入版本，但固定文件只意味着输入不再变化，不证明源数据来自严格一致的全库时刻。

## 第二步：初始化时也会有修改

在初次扫描时，101 的答案从 A 变成 B。查询返回旧值，日志又给新值，哪一个最后应用？连接器要通过快照/日志边界或回填窗口处理。Netflix 方法和 Debezium 流程提供了不同实现参考，但不能随意混搭。[DBLog 方法](https://arxiv.org/pdf/2010.12597)、[Debezium](https://debezium.io/documentation/reference/stable/connectors/mysql.html)

对普通定时查询，也不能凭“查询开始时间”就推导出安全增量起点。长事务提交、业务时间戳写入时刻和数据库读取一致性都会影响边界。

## 第三步：把进度分成三个位置

| 进度 | 实际含义 | 能否直接用于恢复？ |
|---|---|---|
| 已读位置 | 来源已经返回到哪里 | 不够，可能仍只在内存 |
| 已落地位置 | 对应数据已可靠写入并可核对 | 可以作为搬运恢复依据，取决于具体协议 |
| 已发布版本 | 数据通过质量和权限检查，允许训练使用 | 是消费边界，不应倒推源日志已完成所有事项 |

**故障例子**：文件成功上传，但进度记录失败。下次任务必须识别相同 batch_id 并核对内容，再决定是否重用；不能覆盖成另一批数据，也不能盲目跳过。

这也是为什么临时对象、已提交批次和发布的 dataset 要区分。

## 第四步：处理五种“删除”

1. 单行 DELETE：捕获器是否发事件，目标是否应用？
2. TRUNCATE：可能不等于逐行 DELETE，连接器可能有单独限制。
3. 级联删除：是否进入当前复制机制可见的变化？
4. 软删除：行还存在，但 status/deleted 字段改变；样本查询是否排除？
5. 权限撤销或保留到期：数据可能仍合法存在于源库，却不再允许此 ML 用途。

Snowflake MySQL 文档中的删除限制说明，测试一种 DELETE 不能替其他情况背书。[官方限制](https://docs.snowflake.com/en/user-guide/data-integration/openflow/connectors/mysql/about)

## 第五步：结构变化不是只加一列

工单 approved_answer 从字符串变成结构化数组；或者新加一个敏感字段。自动同步新字段能降低维护工作，也可能扩大复制范围。因此需要“结构兼容”与“授权允许”两个检查。

建议：未知字段默认不进入已批准输出，原始区是否允许接收也单独定义；不兼容变更阻止新版本发布。已有旧版训练可以继续引用，但不能把失败批次混进去。

## 第六步：把发布做成明确动作

建议由元数据服务维护状态：

```text
PLANNED → RUNNING → STAGED → VALIDATED → PUBLISHED
               ↘ FAILED / CANCELLED
```

发布记录指向不可变 manifest。文件全部上传不自动等于 PUBLISHED；清洗或授权复核失败时，训练看不到该版本。目录服务中的事务/条件更新要独立验证，不能期待对象存储跨多个文件自动原子提交。

“至少一次输入 + 幂等处理 + 发布幂等”往往比一个未限定范围的 exactly-once 口号更容易验收。幂等的意思是同一批内容重试不会产生第二个不同的可见结果。

## 日志保留与恢复需要一起算

建议以最坏情况规划：调度间隔 + 停机时间 + 追赶时间 + 安全余量，小于可用日志窗口；还需确认追赶吞吐持续高于变化产生速度。公式是容量分析，不是任何产品的 SLA。

如果无法满足，就持续采集到可控缓冲，或接受重新建立基线。不能在恢复点丢失后静默从当前最新位置开始，然后宣称没有漏数。
