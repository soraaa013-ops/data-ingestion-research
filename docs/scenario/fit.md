# 与现有 ML 平台的匹配分析

依据用户已提供场景，不额外假设数据规模、实时性、源版本或组织流程。关联厂商资料见[目录](../vendors/index.md)。

## 现有设计逐项评估

| 当前机制 | 保留价值 | 缺口 | 建议 |
|---|---|---|---|
| 空间管理员配置凭据 | 连接配置集中 | 配置权不等于数据使用权 | secret_ref 与 DataGrant 分开 |
| 用户 DSL | 领域用户能精准选数据 | 任意查询成本及越权边界 | 按来源解析最终表达式并约束数据对象 |
| SELECT 防护 | 降低部分写操作风险 | 读操作仍可能昂贵；非 SQL 无法覆盖 | 权限、计划、预算、超时、服务端取消组合 |
| Kubernetes Job | 批任务隔离、重试和调度 | 不隔离源数据库；不适合任意停启 CDC | 保留批执行器，持续捕获另设运行模型 |
| 文件上传 OBS | 可复用现有 dataset | 中间文件、重复与部分发布 | manifest + READY 发布记录 |
| 每领域自行取数 | 无需统一湖仓 | 同源多空间叠加负载 | 源级预算跨空间共享 |

## 三个假设场景的推演

A：偶尔取一个领域的已完成会话，允许天级新鲜度。优先有限范围批量导出；若主库预算不足则副本/快照。不为了未来可能实时而现在建立常驻 CDC。

B：每天补充会话且旧标签会更正。只按新 ID 抽取会漏修订；可靠更新时间 + 幂等合并可作为候选，物理删除需要对账或 CDC。

C：多个团队持续消费同一来源且需要增删改。可共享一条授权范围明确的捕获通道，再按不同用途生成 dataset；共享缓冲不能扩大任何租户权限。此时持续采集的固定成本可能被摊薄。

这些是条件化案例，不是对实际生产量级的断言。

## 选型门槛

必须项：目标对象存储可达；范围授权可落实；取消/限额有效；重复和删除语义明确；训练版本可复现。任一不满足，产品再丰富也不能直接采用。

偏好项：复用现有基础设施、按需成本、来源覆盖、运维恢复难度。暂不打数值总分，缺少部署和负载参数时精确评分会造成虚假确定性。

## 自建和采购边界

自有平台负责用户意图、授权绑定、样本构建、dataset 发布和训练血缘。可外接批量复制或 CDC 产品。适配接口返回文件/事件及检查点，而不是让外部产品直接决定训练数据可见性。
